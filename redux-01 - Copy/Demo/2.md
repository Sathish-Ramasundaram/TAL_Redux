## 1️⃣ Introduction to Sagas — Purpose & Benefit

**Explain like this:**

> Redux-Saga is a middleware used to handle asynchronous and side-effect logic like API calls, delays, cancellation, and background tasks outside React components and reducers. It keeps reducers pure and moves complex async workflows into sagas.

**Why it’s better than putting async in components:**

> It separates UI from async business logic and makes flows easier to control and test.

**In my project:**

* login API
* OTP flow
* chat send
* bundle parallel fetch
* background sync
* undo throttle

## 2️⃣ Setting Up a Saga

**Explain:**

> We set up Redux-Saga by creating saga middleware, attaching it to the Redux store, and running a rootSaga that contains all watchers.

**Steps you did:**

```
createSagaMiddleware()
configureStore({ middleware: saga })
sagaMiddleware.run(rootSaga)
```

## 3️⃣ Effects — Saga Superpowers

**Explain:**

> Effects are special instructions we yield inside sagas. They tell the middleware what to do — like call an API, dispatch an action, wait, or listen for actions.

### Key effects you used:

| Effect   | Meaning               | Your Example     |
| -------- | --------------------- | ---------------- |
| call     | call async function   | loginApi         |
| put      | dispatch action       | loginSuccess     |
| take     | wait for action       | OTP submit       |
| fork     | start background task | sync worker      |
| select   | read store            | inventory check  |
| all      | parallel calls        | dashboard bundle |
| race     | first wins            | OTP timeout      |
| cancel   | stop task             | sync stop        |
| throttle | rate limit            | undo mail        |

---

## 4️⃣ Generator Functions

**Explain:**

> Sagas are generator functions (`function*`). They can pause and resume using `yield`. This allows step-by-step control over async flows.

---

## 5️⃣ Handling Errors

**Explain:**

> We use try/catch inside saga workers to catch API errors and dispatch failure actions.

**Your example:**

```
try → call API
catch → put(loginFailure)
```

**takeEvery vs takeLatest:**

> takeLatest keeps only the newest request (login).
> takeEvery runs all requests (chat messages).

You used both correctly.

## 6️⃣ Testing Sagas

**Explain simply :**

> Sagas can be tested by stepping through yielded effects and verifying expected effects using redux-saga-test-plan or Jest.

## 7️⃣ Best Practices

**Explain:**

> Best practice is to keep sagas feature-based, separate watchers and workers, keep reducers pure, and move async logic into sagas instead of components.


✅ separate slice per feature
✅ worker + watcher pattern
✅ saga.ts centralized
✅ async only in sagas
✅ reducers only update state
